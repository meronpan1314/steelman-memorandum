## 結論

DRY原則とは、**同じ知識・同じ判断・同じロジックを複数箇所に重複して書かない**という設計原則である。

DRYは **Don't Repeat Yourself** の略。

一言でいうと、**「同じことを何度も書くな」ではなく、「同じ変更理由を複数箇所に散らすな」** という考え方。

---

## 1. DRY原則とは何か

DRY原則は、ソフトウェア開発における重複を減らすための考え方。

例えば、消費税率をいろいろな場所に直接書いているとする。

```java
int priceWithTax = price + (int)(price * 0.1);
int feeWithTax = fee + (int)(fee * 0.1);
int totalWithTax = total + (int)(total * 0.1);
```

この場合、税率が変わったら複数箇所を修正しなければならない。

修正漏れがあると、場所によって計算結果が変わる。

DRY原則では、このような「同じ知識の重複」を避ける。

---

## 2. なぜ重要なのか

重複したコードは、変更に弱い。

同じロジックが複数箇所にあると、以下の問題が起きやすい。

- 修正漏れが起きる
- 仕様変更時の影響範囲が広がる
- バグ修正を複数箇所に反映する必要がある
- どれが正しい実装なのか分からなくなる

つまりDRY原則は、コードを短くするためではなく、**変更に強くするための原則**である。

---

## 3. 悪い例

### ■ 同じ判定が複数箇所にある

```java
if (user.getAge() >= 20 && user.isVerified()) {
    // 購入可能
}
```

```java
if (user.getAge() >= 20 && user.isVerified()) {
    // キャンペーン対象
}
```

この判定が「18歳以上」に変わった場合、両方を修正する必要がある。

片方だけ修正すると、仕様のズレが発生する。

---

## 4. 改善例

判定ロジックをメソッドにまとめる。

```java
public boolean canUseService(User user) {
    return user.getAge() >= 20 && user.isVerified();
}
```

利用側は、そのメソッドを呼び出す。

```java
if (canUseService(user)) {
    // 購入可能
}
```

```java
if (canUseService(user)) {
    // キャンペーン対象
}
```

条件が変わったときは、`canUseService` だけを修正すればよい。

---

## 5. DRYが守れている状態

DRYが守れているコードは、以下のような状態になっている。

- 同じ業務ルールが1箇所にまとまっている
- 定数や設定値が散らばっていない
- 同じSQLや同じ条件式が複数箇所にない
- 変更時に修正する場所が明確

重要なのは、**コードの見た目が似ているか**ではなく、**同じ知識を表しているか**。

---

## 6. やりすぎに注意

DRY原則は大事だが、何でも共通化すればよいわけではない。

たまたま見た目が似ているだけの処理を無理にまとめると、逆に分かりにくくなる。

### ■ 悪い共通化

```java
public void process(Object target, String mode) {
    if (mode.equals("user")) {
        // ユーザー処理
    } else if (mode.equals("order")) {
        // 注文処理
    }
}
```

このような共通化は、責務が曖昧になりやすい。

DRYを意識しすぎて、何でも1つにまとめると、変更に強いどころか変更しづらくなる。

---

## 7. DRYとWET

DRYの反対に近い考え方として、WETという表現がある。

WETは文脈によって以下のように説明される。

- Write Everything Twice
- We Enjoy Typing

つまり、同じことを何度も書いている状態。

ただし、最初から無理にDRYにしすぎるより、処理の意味が見えてから共通化した方がよい場合もある。

---

## 8. 実務での見方

DRY原則を見るときは、以下を確認する。

- 仕様変更時に何箇所直す必要があるか
- 同じ業務ルールが複数箇所に存在しないか
- 共通化によって逆に責務が曖昧になっていないか
- 「見た目の重複」ではなく「知識の重複」を減らせているか

特に業務システムでは、金額計算、権限判定、ステータス判定などを重複させないことが重要。

---

## 9. まとめ

- DRYは Don't Repeat Yourself の略
- 同じ知識やロジックを複数箇所に重複させない原則
- 目的はコードを短くすることではなく、変更に強くすること
- 見た目が似ているだけの処理を無理に共通化しない
- 業務ルール、定数、判定条件、計算ロジックの重複に注意する
